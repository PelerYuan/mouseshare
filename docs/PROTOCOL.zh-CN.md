## 设备发现

以 *被控端* 身份共享的电脑会通过 mDNS / DNS-SD 以 `_mouseshare._tcp.local.` 对外广播，并带有两个 TXT 记录：

| 键 | 值 |
|---|---|
| `screen_id` | 设备名称 |
| `protocol_version` | 它使用的协议版本 |

广播内容**不含任何机密**。发现是可选的：控制端总可以直接指定 `host:port`。

## 传输与分帧

每对控制端 ↔ 被控端使用一条 TCP 连接（默认端口 `7878`，开启 `TCP_NODELAY`）。每条消息是一个**帧**：

```text
+----------------+---------------------------+
| length: u32 BE | body（length 字节）        |
+----------------+---------------------------+
```

- 密钥交换完成之前，帧里是原始的 SPAKE2 消息（最多 256 字节）。
- 之后，body 是 `ChaCha20-Poly1305(bincode(Message))`（含 16 字节标签），`length` 覆盖整个密文。
- 超过 `MAX_FRAME_LEN`（1 MiB）的帧会在分配内存*之前*被拒绝，所以恶意的长度前缀无法耗尽内存。

消息使用 [bincode](https://docs.rs/bincode) 序列化。

## 安全设计

**目标。** 只有知道配对码的人才能控制一台电脑或读取其通信，即使在不可信的网络上；并且配对码要短到可以手输，
所以不能被离线破解。

**配对码。** 10 个 Crockford base32 字符（`0-9 A-Z`，去掉 `I L O U`），显示为 `XXXXX-XXXXX`，
共 50 位，来自操作系统随机源。输入不区分大小写，并容忍相近字符（`O→0`、`I/L→1`）。

**握手**（双方只知道配对码）：

1. 拨号方 → 监听方：SPAKE2 消息 A（33 字节）
2. 监听方 → 拨号方：SPAKE2 消息 B（33 字节）
3. 双方计算 SPAKE2 共享密钥 `K`（Ed25519 群，身份标识 `mouseshare-v2-dialer` /
   `mouseshare-v2-listener`），再用 HKDF-SHA256（以 `SHA-256(A ‖ B)` 为盐）派生出两个 32 字节密钥，
   每个方向一个（`"mouseshare v2 dialer->listener"`、`"mouseshare v2 listener->dialer"`）。
4. 拨号方发送加密的 `Hello`，监听方回复加密的 `HelloAck`。每个方向上的成功解密**就是**双向密钥确认。
   配对码错误时密钥不同，第一个 AEAD 标签校验失败，连接被丢弃，不会泄露任何其他信息。

**记录层。** ChaCha20-Poly1305，96 位 nonce 为每个方向严格递增的计数器（因为密钥按连接、按方向独立，所以是安全的）。
被重放、乱序、丢失或篡改的记录都会认证失败并结束会话。

**为什么用 PAKE。** 配对码很短，如果直接用它做 MAC/AEAD 的密钥，窃听者可以每秒数十亿次地离线试错。
SPAKE2 把每一次猜测都变成一次*在线*连接尝试。

**在线猜测。** 被控端对每个来源地址每 60 秒最多容忍 **5 次握手失败**，之后丢弃来自该地址的尝试。
在 50 位的强度下，暴力破解毫无希望。

**能防护：** 被动窃听、主动中间人、重放、其他主机注入输入、对截获流量的离线破解。

**不能防护：** 已经掌握配对码或 `pairing.toml` 的人（请像对待密码一样对待它们）、任一电脑上的恶意软件、拒绝服务
（网络上的攻击者仍可使连接失败）。如果配对码泄露，之后任何人都可以冒充对端，请重新生成配对码；
但仅凭配对码无法解密过去截获的流量。

监听方同一时间只接受**一个控制端**；已有连接时会拒绝第二个连接。

## 消息

`crates/protocol/src/lib.rs` 中的 `enum Message`。`dx/dy` 为正表示向右/向下。

| 消息 | 方向 | 含义 |
|---|---|---|
| `Hello { version, device_id, monitors }` | 控制端 → 被控端 | 第一条加密消息：协议版本、控制端名称及其显示器。 |
| `HelloAck { version, device_id, monitors }` | 被控端 → 控制端 | 回复被控端的名称和显示器。 |
| `MouseMove { dx, dy }` | 控制端 → 被控端 | 以被控端像素为单位的相对移动（已按设备的指针速度缩放）。 |
| `MouseWarp { x, y }` | 控制端 → 被控端 | 把指针放到被控端根坐标系中的绝对位置；控制权进入该设备时发送，使光标出现在穿越点。 |
| `MouseButton { button, pressed }` | 控制端 → 被控端 | X11 按键编号（1 左、2 中、3 右、8/9 后退/前进）。滚轮按键 4–7 从不通过它发送。 |
| `Scroll { dx, dy }` | 控制端 → 被控端 | 滚轮格数。`dy` 为正向下滚，`dx` 为正向右滚。 |
| `KeyEvent { keycode, pressed }` | 控制端 → 被控端 | 原始 X11 键码的按下/释放。 |
| `ClipboardText(String)` | 双向 | 发送方的剪贴板变成了这段纯文本。 |
| `Ping(u64)` / `Pong(u64)` | 双向 | 延迟探测和存活检查；`Pong` 回显令牌。 |
| `MonitorsChanged(Vec<MonitorInfo>)` | 双向 | 显示器热插拔或分辨率变化。 |

`MonitorInfo { name, x, y, width, height, primary }` 使用发送方自己的根窗口坐标；最左边显示器的左上角不一定是 `(0, 0)`。

## 会话生命周期

1. 控制端解析被控端地址（显式给定或通过 mDNS），拨号（5 秒超时）并执行握手（10 秒超时）。
2. 双方在 `Hello` / `HelloAck` 中交换显示器列表；控制端据此把被控端放进排列。
3. 光标在控制端自己的屏幕上时，只有 ping 和剪贴板文本在流动。光标穿过边缘后，控制端先发 `MouseWarp`，
   然后持续发送 `MouseMove`、`MouseButton`、`Scroll` 和 `KeyEvent`；输入在本地被捕获，不再送给本地窗口。
4. 每 2 秒发送一次 `Ping`。如果 10 秒内没有任何数据，链路被判定为失效：被控端上按住的按键会被释放，
   光标回到控制端，监督任务按指数退避（1 秒 → 15 秒）重连。
5. 紧急返回快捷键在控制端本地匹配，从不转发。

## 坐标与显示器

每台设备拥有一组**刚性**的显示器，被放置在共享的*虚拟桌面*中。边缘检测在设备所有显示器的*并集*上进行，
所以只要两台设备的显示器相接，光标就能穿过，并从对应位置进入（`MouseWarp`）。不同分辨率直接按像素处理，
与真实多显示器系统的模型一致，不做自动比例缩放；请用 *对齐* 来决定屏幕相接的位置。

## 版本管理

`Hello.version` 携带协议版本。版本不匹配会报告为不兼容错误并关闭连接。同一版本内不会新增消息变体，
对传输格式的任何改动都会提升版本号。
